# Adversarial source review: alpha.11

The alpha.10 adversarial review identified eight defects or protocol ambiguities. This record preserves their alpha.11 corrections and regression checks. Earlier findings are in the [alpha.9](REVIEW-2026-10.md) and [alpha.10](REVIEW-2026-10-SECOND.md) records; [VALIDATION.md](VALIDATION.md) lists current results.

## Erasure and reconnect protocol

Each paired device has a persisted `gps_epoch`. Existing server rows receive one during migration; enrollment supplies one, and signed command polling/sync/telemetry responses carry the current value. It is a generation marker, not a credential. Authentication still comes from WireGuard and the phone-held signing key.

The phone persists that generation encrypted, separately from observation timestamps. Its one encrypted journal belongs to that generation. When reconciliation sees a different generation, the fence cancels pending work, clears the journal and legacy queues, then persists the new marker. Clear happens before marker persistence: interruption can lose unsent readings, but cannot attach an old queue to a new generation. A sampling stamp taken before reconciliation cannot append afterward. New GPS observations must come from sensor updates whose elapsed timestamp is after that capture request started; old OS cached fixes are never relabeled into the new generation.

An offline phone may continue collecting into its old generation until it reconnects. The server refuses those GPS points even if they were captured after the administrator's erase but before the phone learned of it. The phone deliberately discards that entire queue and begins fresh observations. This prioritizes erasure over preserving an ambiguous backlog. GPS/check-in/IP data already committed after an erase remains subject to ordinary explicit erasure; erasure does not stop ongoing sharing. A phone/server backup restore can reintroduce historical data/generations and is a separate operator recovery operation, not a new privacy acknowledgment.

**Upgrade server first, then APK to alpha.11.** Old GPS payloads lacking a generation receive 409 instead of a false successful acknowledgment. The first alpha.11 reconciliation on an upgraded phone clears any old untagged backlog because its relationship to earlier erasures cannot be proven. This one-time loss is explicit; it does not erase existing home history or unpair the phone. Retain the same APK signer for in-place upgrades.

## Exact local withdrawal boundary

GPS-off persists withdrawal and clears local unsent GPS. The fence prevents an earlier prepared batch from obtaining a new valid reservation, invalidates old captures across an off/on cycle, cancels active GPS requests and signals native HTTP cancellation. A command withdrawal cancels remote locate even if periodic GPS sharing remains enabled. Local stop applies to both. No network wait occurs under the fence monitor; only short reservation/cancellation, local state and Android listener operations do.

Cancellation is not recall. A request already handed to the transport may have delivered some/all of its body; home may finish a transaction it already received. Without contact with home, the phone cannot prove a remote deletion or distributed commit barrier. The UI says pending sends are canceled and already-sent data remains at home until erased. Use administrator GPS/full-history erasure to rotate the home generation and invalidate old prepared/in-flight GPS transactions at their server write boundary. That operation also cannot retract a previously downloaded/exported copy.

Preference/write errors are surfaced. GPS and command consent fail closed in the current process; a failed local-safety write also keeps a process veto. Complete storage failure still cannot promise durable withdrawal across process death. Independent recovery and Android force-stop/uninstall remain escape paths. The recovery entry point still initializes neither Identity nor the native transport; its fence only invokes callbacks when active operations have registered them.

## History resource contract

Normal unfiltered history retains paginated access to old data; these limits do not delete history. An interval filter must span at most 366 days and 10,000 anchored buckets. Daily filtering retains the existing 366-day bound and timezone/DST rules. JSON pages contain at most 1,000 records and use at most two read workers for five seconds each; extra requests get 429 and an interrupted/timed-out query must be retried with a smaller range. Handler cancellation sets the worker cancellation flag; SQLite progress checks interrupt canceled scans. CSV keeps its separate two-worker, five-minute streaming limit; interval selection has the same bucket/span limits as JSON.

Read snapshots use separate read-only connections and never hold the canonical write mutex during the scan. Final session/revocation/history-revision checks use current state. A change detected before delivery rejects the JSON response; bytes already sent cannot be recalled. Reads can still consume CPU, temporary storage and retain WAL pages until completion/cancellation. This is resource isolation with finite limits, not an availability proof for arbitrary storage/hardware.

## D findings: implementation and verification status

- **D-01 — publisher authentication:** registry TLS, repository constraints and digests do not independently authorize a publisher. Signature/provenance verification, pinned trust roots and tested key rotation/revocation/replay handling remain unimplemented. No publisher key was invented or represented as trusted.
- **D-02 — backup encryption:** updater snapshots remain root-only plaintext tar archives with checksums. Require encrypted trusted persistent/snapshot storage; encrypt external copies separately with recovery keys held separately. Existing plaintext blocks/copies are not retroactively erased. Built-in authenticated archive encryption and hostile/lost-key restore drills remain open.
- **D-03 — physical acceptance:** no physical GrapheneOS lifecycle, power-loss or storage-fault campaign was run here. Host tests, compilers and fake transport schedules cannot establish sensor, Keystore, Android binder/service, Doze or firmware behavior.

The supported configuration remains a removable personal app, with no automatic history expiry or runtime map/DNS/analytics provider.

## Remaining acceptance work

On an isolated supported GrapheneOS handset, record exact OS/APK hashes and verify: GPS-off during capture, after batch preparation and during slow upload; command-off/local stop during locate; fast off/on cycles; first-upgrade queue clearing; process death on either side of queue-clear/epoch persistence; lost Keystore/storage faults; generation change while offline; boot/first unlock/Doze; other VPN coexistence; recovery/Android Settings deactivation and uninstall. Capture only synthetic positions and owned-server traffic. Verify that cancellation cannot start another send, that already-received bytes are described accurately, and that every stop remains locally recoverable.

On isolated home hardware, test server power loss around erase/upload commits, sustained history/CSV contention and low-storage/WAL behavior, real Caddy traversal and update rollback. A historical restore can reintroduce erased records; snapshots and downloaded CSVs need separate retention/disposal controls.
