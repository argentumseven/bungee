## Export resource and privacy boundaries

CSV uses one read-only SQLite statement snapshot rather than retaining every row in JavaScript. SQLite's page cache is limited for each export, and interval grouping can use temporary disk files. Long readers retain WAL state until they finish or cancel; the five-minute/two-worker bounds limit that exposure. Operators still need free database/WAL/temp/download storage. A slow or very large export may require a smaller time range. Downloads contain sensitive plaintext location history: store them on encrypted media.

An already transmitted or buffered byte cannot be recalled by erasure or logout. The server stops producing further chunks after detecting loss of authorization or a changed erasure revision; it does not claim to erase downloaded copies. Cancellation uses the browser's ordinary Downloads controls and HTTP disconnect. Changing dashboard tabs does not silently cancel a download the owner requested.

## Additional state handling checked during remediation

WireGuard public/private preference creation now commits as one update. The app derives a missing/mismatched public key from the existing private key instead of replacing that private key. Initialization and explicit reset share a lock across identity instances; an unenrolled identity cannot enqueue new fixes. A missing signing/encryption key for existing identity material causes a visible recovery path, rather than silently generating replacement keys. Invitation and recovery-message removal writes also check persistence. No root, owner enrollment, radio automation, wipe, credential change or persistent restriction was introduced.

These additional changes compile and pass lint; Android Keystore interruption, identity corruption, process death during initialization and actual settings interaction remain physical acceptance work. Lost keys cannot be reconstructed by a source change. Local recovery and Android Settings remain available independently of loading the encrypted identity.

## Deployment requirements still open

- **Publisher-authenticated updates:** registry TLS, fixed repositories and digests still do not enforce publisher signatures/provenance. No new authenticity guarantee is made.
- **Built-in encrypted snapshot archives:** updater tar snapshots remain plaintext with restrictive permissions/checksums. Encrypt both persistent volumes and updater storage; encrypt exported backups independently and test key recovery.
- **Physical GrapheneOS acceptance:** cold boot/first unlock, background GPS, Doze, multiple days offline, low storage, permission revocation, updates, another VPN and independent local recovery remain unverified on a real phone.
- **Administrator authority/reachability:** MFA/roles, administrator recovery, dynamic numeric endpoint changes and provider-free relay/CGNAT recovery remain open. The two-minute signature clock window remains enforced.
- **Accessibility/endurance:** screen readers, large fonts, contrast/touch targets, long exports over real home networks, battery/flash endurance and power-loss behavior still need testing.

Indefinite server location history remains the owner's explicit policy. This review did not authorize automatic age-based deletion, provider fallbacks, device-owner enrollment or irreversible phone controls. Bungee still must not be relied on as the sole means of recovering an important phone.

## Physical acceptance additions

In addition to [the original device checklist](REVIEW-2026-10.md#physical-device-acceptance-before-relying-on-recovery), verify fresh and upgraded installations start with all household commands off. Pair and confirm GPS telemetry without permitting ring/message/lock/fresh-location commands. Explicitly enable commands with local phone unlock, then withdraw while a sound or lost mode is active. Inject preference-write/read failures; check the error, current-process veto, independent stop attempt, restart behavior and Android force-stop path. Repeat for app-lock persistence. Never use a main phone to establish these guarantees.

Use isolated synthetic servers for interruption/restore tests. Kill the server before/after each database commit and peer publication, then verify canonical resynchronization, safe reissue, old token/PSK invalidation and protection of unrelated paired history. Export a large range through the actual home Caddy path, cancel it, erase history during it and revoke its session; verify partial downloads report failure and no export continues indefinitely.
