# Migrate a 1.1.4 deployment

The new installer provisions a fresh LUKS2 filesystem and refuses old installations or volumes. Migration is a local-console maintenance operation. Do not attempt it through the dashboard or with active clients. Keep independent encrypted recovery copies before retiring plaintext storage. The phone protocol and SQLite schema remain compatible; preserving the WireGuard identity, peer secrets and database preserves enrollment.

1. Record the existing configuration, administrator origin/prefixes, endpoint and ports. Disable the old update timer. Close admission with the old host helper's maintenance control and wait for the gateway to report `closed`. Disable container restart policies, then stop/remove the old containers with their exact Compose file **without `--volumes`**. Confirm no Bungee container is running. SQLite and all key/peer files must be cold before copying.
2. On encrypted offline media, create a dedicated age identity with `age-keygen -o recovery-identity`. Keep it separately from ciphertext. For each of the five old project-owned volumes (`bungee_server-data`, `bungee_gateway-private`, `bungee_gateway-peers`, `bungee_caddy-data`, `bungee_caddy-config`), verify its Docker Compose project/volume labels. Use a local trusted image, no network, root filesystem read-only and a read-only source-volume mount to stream `tar -cpf - -C /data .` through `age -r RECIPIENT > volume.tar.age`. Enable shell `set -o pipefail`; any tar or age failure invalidates the backup. Do not write a plaintext tar first. Authenticate each result with `age -d -i recovery-identity volume.tar.age > /dev/null`, and inspect an authenticated decrypted listing. Record checksums of all ciphertext files.
3. Also encrypt the entire old host installation directory, including its plaintext rollback backups and configuration. Verify that archive. Retain copies on independent encrypted media. Recheck that the cold source database, server WireGuard key and peer-secret configuration are included. Test extraction on encrypted scratch storage before retiring any source.
4. After verifying those independent recovery copies, retire the old named volumes and move the old installation out of the new mount path. These are deliberate destructive operations on the old installation; never use a broad Docker prune. Retire old plaintext backups and provider snapshots too. SSD/cloud deletion is not a guaranteed secure erase; an earlier plaintext copy may remain recoverable from its storage provider. The new code cannot retroactively encrypt those snapshots.
5. Install with the new host helper using the recorded endpoint, ports and administrator restrictions. It creates the encrypted mount, new host keys and a new local HTTPS CA. Keep phones offline during this initial empty-state start. Close admission, disable container restart policies and stop the new stack before replacing its state.
6. On the encrypted mount, replace the new `volumes/server-data`, `volumes/gateway-private` and `volumes/gateway-peers` contents with the corresponding authenticated cold archives. Extract only these known archives, locally as root, into their matching directories. Preserve ownership/modes. Keep the new `volumes/tls-data` and new host metadata; do not restore old Caddy paths into them. Restore offline map datasets through the new dataset command. The old Caddy volumes remain only in the encrypted recovery copy.
7. Run the new helper's `recover --start`. Verify service health, the retained WireGuard server public key, existing devices/history and administrator login before reopening phone access. Trust the new public root certificate after verifying its fingerprint locally. Verify a real phone reconnects and a fresh encrypted rollback archive can be authenticated and restored on encrypted scratch storage.
8. Reboot from the console and verify automatic unlock, mount-before-Docker ordering, maintenance recovery, HTTPS source restrictions and the separate WireGuard device API. Keep the old recovery identity until its recovery archives are intentionally retired.

Do not copy a live SQLite database or mix data/keys from different snapshots. If any step fails, keep admission closed and recover from a verified cold archive. Do not reopen the old plaintext deployment as an automatic fallback.
