No real household data or physical device is used by the test fixtures. The DNS suite explicitly seeds an old-policy fixture for compatibility isolation/erasure; it is not evidence that new managed DNS enrollment is allowed. Browser DNS rows are synthetic saved legacy data.

The emulator attempt uses a dedicated Android 16 AOSP x86_64 virtual device without KVM. Its identity is checked before commands. No physical phone is targeted. Standard host ADB cannot write its fixed home configuration path in this sandbox; a direct ADB protocol client is used only against the owned loopback emulator. Slow software emulation caused early package-install attempts to be rejected while booting, followed by Android system-service restarts/timeouts. Increasing only this emulator's supported watchdog timeout to 600,000 ms did not produce a usable interactive test. An intermediate APK eventually installed and an app task appeared, but local stop, ordinary admin deactivation, corrupted-state recovery, Settings navigation and cold-boot assertions could not be completed. The owned emulator was stopped. These observations are not passed app-runtime tests; the final APK still needs them.

The operator signing helper previously passed with a disposable test key; no production key has been generated/distributed. Device-owner enrollment remains unsupported with any signer. Personal-app signer changes can require uninstall/re-pair and erase Bungee's own local identity/backlog, not the phone's other data.

Remaining lint warnings include synchronous preference persistence (intentional for stop/receipts), translation/KTX suggestions, and an ImplicitSamInstance warning on Context.stopService(Intent). The latter API identifies the service by its explicit component rather than Intent object identity; no listener is being removed. The newer foreground-service fallback type is now gated to Android 14+, with the pre-14 fallback explicitly using NONE. Runtime behavior still requires device checks.

The local-stop failure tests inject exceptions into the coordinator; they do not prove all Android APIs, filesystem failure modes or hardware behavior. Logical history erasure/backups, storage capacity, concurrent exports and restoration still need load/fault testing. No audit, hardware attestation, whole-phone zero-provider traffic or fully quantum-proof product claim is made. Certificate/device/APK signatures remain classical.

The alpha.8 build initially exhausted the cloud workspace disk; only unused Docker build cache was pruned and generated installer archives were moved to temporary storage. Source, persistent volumes and release APKs were preserved. A clean Android build and fresh container build were then used for final validation; the earlier failed build is not counted as a pass.

No publisher-signature or backup-encryption implementation is claimed.

## Version 1.1.1 persistent theft-photo consent and restart recovery

Camera protection now uses one standing local opt-in rather than requiring a fresh approval after every process loss. Initial enablement remains locally authenticated and visible. Android system sticky restoration requires a saved encrypted checkpoint from the same OS boot; it preserves the failure streak, consumed-attempt budget and unsent encrypted photo queue. Eligible successful-credential callbacks can reset the saved streak before the camera service is restored, without starting it. A callback returning from the phone's credential activity waits for Bungee's resumed lifecycle before executing the approved action. Explicit disarm, local stop, command withdrawal and ordinary-administration deactivation disable automatic camera recovery; clearing local stop does not restore that opt-in. Bungee's notification actions request Android authentication before stopping sharing or disarming camera protection. Stopping sound remains separate.

The Android JVM suite passes **52 tests**, zero failures/errors/skips. Six added cases cover same-boot restoration without duplicate streak capture, preserved successful-unlock reset and rolling attempt limits, absent/cross-boot checkpoint rejection, corrupt/future checkpoint rejection, camera consent's connection-restart scope and stop/clear-stop withdrawal, and independent sharing restart consent after camera disarm. These are real policy/checkpoint tests, not Android service-lifecycle or camera-hardware tests. Debug and R8-optimized unsigned release builds and both lint checks pass with nonfatal warnings and no errors. The signed debug APK reports **1.1.1/code 17**, keeps the 1.1.0 local debug signer, passes signature/16-KiB ZIP alignment checks and has the same merged permissions. The local-recovery launcher, disabled owner-provisioning activities and absence of a VpnService are checked in the APK. No production signing key is configured.

Rust fmt, Clippy for all targets with warnings denied, the locked build and **13 Rust tests** pass. **99 API**, **18 browser** and **24 host** tests pass, with zero failures/skips. TypeScript/Vite builds; the dashboard distinguishes last-reported readiness from its saved opt-in and offline uncertainty. Pending-photo reports read the retained encrypted queue even while the camera service is unavailable, rather than reporting a fresh process-local zero; queue-read failure omits the camera report without blocking ordinary telemetry. The phone waits for a ready session before showing its queue counters. Thirteen dark browser fixture screenshots are regenerated; no browser runtime errors or provider requests are observed. The unchanged native transport/race suite is historical evidence, not rerun by this lifecycle change.

All three container images build. The 1.1.1 Rust image runs in an actual isolated container as UID 10001, with read-only root, all capabilities dropped, no new privileges and no external network. Health/version, session authentication, unauthenticated photo denial, authenticated missing-device isolation and matching dashboard/brand assets pass. Full gateway/TLS/source-ACL/update-rollback tests remain historical and were not rerun because those implementations are unchanged. No stable release tag or automatic-update promotion is created.

**Always-armed operation through reboot or force-stop is not established or claimed.** Reboot, GrapheneOS automatic reboot, APK replacement or Android app/service stop can require opening unlocked Bungee once; standing consent then resumes without a new dialog. A boot receiver and failed-password/server callbacks do not start the camera service. Physical GrapheneOS locked/background capture, actual sticky restart admission/timing, notification authentication, credential callbacks during process recovery, privacy controls, battery/Doze endurance, storage faults and reboot/update recovery still require the documented device acceptance procedure. Existing removable-app controls and independent local recovery remain available.
